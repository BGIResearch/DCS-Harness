# 发布与版本号规则

版本号的唯一基准是**上一次真正发布**的版本（npm 上有、git 上有同名 tag）。
没发布就不算版本——版本号只反映“已经交付的东西”。

## 规则

1. **未发布期间只升小版本（patch）**：`2.17.3 → 2.17.4 → 2.17.5 …`。
   只要上次发布之后还没发新版本，任何改动（哪怕是新功能）都只 +patch，
   **不允许跳 minor 或 major**（`2.17.3 → 2.18.0` 属于违规）。
2. **只有发布时才允许升 minor**：先把代码定稿，再一次性做
   `改版本号 → 更新 CHANGELOG → npm publish → git tag`；tag 与 npm 版本必须同名同值。
   发布完成后 `package.json` 版本 == 最近 tag，进入“干净状态”。
3. **三处同步**：`package.json` 的 `version`、`CHANGELOG.md` 的 `## [x.y.z]` 标题、
   `git tag vx.y.z` 必须一致；发布前跑 `node scripts/check-version.mjs` 自检。
4. **不要用 feature 提交顺手改 minor**：功能提交里把 `2.17.3` 改成 `2.18.0` 是历史事故
   （结果是 npm 停在 2.17.3、仓库里却写着 2.19.0，中间两个版本从未存在）。

## 为什么

- npm 用户只能看到已发布版本；仓库里的数字跳得再高也交付不了任何东西。
- 跳号会让 `git describe`、按 tag 推导版本的脚本、以及下游依赖全部失真。
- 真正的版本语义由发布动作定义，不由提交里的字符串定义。

## 检查

```bash
node scripts/check-version.mjs      # 未发布窗口内必须同 minor、patch 递增
```

规则映射：

| 最近 tag | package.json | 结果 |
|---|---|---|
| v2.17.3 | 2.17.3 | ✅ 干净（已发布） |
| v2.17.3 | 2.17.4 / 2.17.5 | ✅ 未发布，小版本升级 |
| v2.17.3 | 2.18.0 / 2.19.0 | ❌ 未发布却跳 minor |
| v2.17.5 | 2.17.4 | ❌ 版本回退 |
